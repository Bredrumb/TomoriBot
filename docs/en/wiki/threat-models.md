## TL;DR

- **Stored provider keys cannot be read out through Discord.** Every credential read is scoped to its owner in SQL, no surface renders a key (not even a masked prefix), credential modals never prefill, and config and memory exports carry no credential columns. See [Key Custody](#key-custody) for the paths that were checked and cleared.
- **The remaining key exposures are host-side and operational**, not reachable from a Discord account: a `SIGUSR2` heap snapshot, a legacy backup bundle that still holds `config.env`, and two subprocess command lines.
- **API keys are encrypted at rest** with `pgcrypto` (AES-256). A full DB dump without `CRYPTO_SECRET` is useless, with three caveats: the plaintext key and the secret are bind parameters of every encrypt and decrypt query, only presence is validated (`.env.example` suggests a 32-character secret), and production copies only `CRYPTO_SECRET`, `_V1`, `_V2`, and `_V3` out of the secrets bundle.
- **One Discord-reachable token leak exists today**: the ComfyUI reference-image download attaches `Authorization: Bot $DISCORD_TOKEN` to any URL whose text contains `discord.com`, because the check is a substring test rather than a hostname comparison.
- **Local MCP servers run with host-level trust, and stdio children receive the entire bot environment.** Any MCP package the operator runs, including the bundled search server that is on by default, can read `CRYPTO_SECRET`, the Discord token, the database URL, and every provider key.
- **SQL injection is defended** by Bun SQL template literals. Dynamic update columns are schema-derived allowlists in four repositories; `ConfigRepository` still interpolates table and column names with type-level protection only, so never pass a request-shaped object into it.
- **Discord roles are the trust boundary: `ManageGuild` in the command loader sets registration defaults rather than runtime enforcement.** Only routes that re-check `memberPermissions` hold; `/config` does, `/persona create`, `/persona export`, `/persona generate`, `/status`, and `/troubleshoot` do not.
- **LLM output is untrusted.** Prompt injection through memories, documents, web pages, and MCP tool descriptions is a real attack surface; use `/tool prompt snapshot` to find the source of a malicious prompt. Treat the server system prompt as public: `/status` prints it to any member.
- **BYO endpoints can see your data, and a stored credential follows its URL.** The key saved for a label is sent to whatever host that label points at, including a redirect target, so an endpoint URL is not a credential boundary.
- **SSRF is mitigated** by `validateRemoteUrl()`, `fetchUserRemoteUrl()`, and `safeDownload()`. New code touching user-supplied URLs must use these helpers. The known exceptions are Crawl4AI (out-of-process rendering), a guild `url_fetcher` MCP that replaces the built-in, and the Matrix avatar and relay downloads.
- **Set quotas, enable BYOK mode, and turn off feature flags you do not need** (image gen, video gen, manage-message, prompt snapshot, MCP, custom endpoints). There is no cross-channel feature flag: restrict `/providers` and the cross-channel blocklist instead.

## 1. Database, Secrets, Key Custody, and Tenant Isolation

TomoriBot stores server configuration, personas, memories, API credentials, managed webhook tokens, Matrix links, custom endpoints, quota state, reminders, and caches in PostgreSQL.

### Key Custody

The production instance holds roughly a thousand registered provider keys across guilds and personal scopes, so the custody question is answered separately from the rest of the database.

| Path | Who can reach it | Current Control | Implementation Area | Residual Risk / Assumption |
| :--- | :--- | :--- | :--- | :--- |
| **Read a stored key through Discord** | Any member, any admin | No surface renders a key, including masked representations. Status and capability surfaces show presence, counts, and rotation size only. Credential modals carry placeholders, never values. Prompt assembly never serializes a credential. Config and memory exports exclude provider tables. | `src/utils/metrics/status/serverConfigPages.ts`, `src/utils/metrics/providerStats.ts`, `src/utils/discord/ui/providersPanel.ts`, `src/utils/db/repositories/ExportRepository.ts`, `src/tools/functionCalls/reviewCapabilities.ts` | Keep it that way: a "show key" affordance, a masked prefix, or a credential field in an export format would open a new disclosure path. |
| **Read another tenant's key** | Any member or admin | Every credential read is owner-scoped in SQL (`server_id` + `provider`, or `user_id` + `provider`), and the endpoint URL and the credential are resolved from the same saved row, so the pair cannot be desynchronized. Rotation pools are writable only from `/providers`. | `src/utils/db/repositories/LlmProviderRepository.ts`, `src/utils/provider/credentialResolver.ts`, `src/utils/provider/customEndpointService.ts`, `src/utils/provider/providerPanelOperations.ts` | Custom endpoint connections are owned by exactly one server or one user (DB check constraint). `registerCustomEndpoint` does not owner-validate an `editingEndpointId` itself; today only owner-scoped callers reach it. |
| **Encryption at rest** | Anyone with a database dump or read access | `pgcrypto` PGP symmetric, `cipher-algo=aes256`, per-row `key_version`. Encrypted columns: `saved_provider_configs.api_key`, `user_saved_provider_configs.api_key`, `api_key_rotation.api_key`, `opt_api_keys.api_key`, `guild_mcp_servers.auth_token`, `discord_managed_webhooks.webhook_token`. `server_model_configs.api_key` is a legacy mirror of the same data. | `src/utils/security/crypto.ts`, `src/db/schema.sql`, `src/utils/db/repositories/ServerRepository.ts`, `src/utils/db/repositories/ToolRepository.ts` | The secret is the raw environment string used as the pgcrypto passphrase, with pgcrypto's default S2K parameters and no application-side KDF, so derived-key strength equals `CRYPTO_SECRET` entropy. A 32-character random secret is the floor. |
| **The secret in transit to PostgreSQL** | Anything that records statements or traffic between the app and the database | None: both the passphrase and the plaintext key are bind parameters of every `pgp_sym_encrypt` / `pgp_sym_decrypt` call. | `src/utils/security/crypto.ts`, `src/utils/db/repositories/ServerRepository.ts`, `src/utils/db/repositories/ToolRepository.ts` | A database-side audit or statement log that records bind parameters (for example `log_statement=all` with the default parameter length), a managed-database operator, or a capture on the app-to-database hop exposes both the secret and every key it protects. Credential design would have to move in-process to remove this. |
| **Plaintext in a heap snapshot** | Anyone who can send `SIGUSR2` to the container, or read the log mount | The handler is armed only when `HEAP_SNAPSHOT_DIR` is set. `/app/logs` is a host bind mount. | `src/init/heapSnapshot.ts`, `release:deploy/azure/docker-compose.yml`, `src/index.ts` | A snapshot serializes the live heap, which holds the plaintext returned by `decryptApiKey` plus `CRYPTO_SECRET`, the Discord token, and the database password. The Azure production compose file sets `HEAP_SNAPSHOT_DIR` to the log mount by default, so a deliberate signal writes every secret to the host log directory. See `docs/en/wiki/production-tuning.md`. |
| **Secrets on disk in a backup bundle** | Anyone who obtains a bundle directory | New bundles hold only `database.sql` and `bundle_info.json`, which lists the key versions the dump needs; `.env` is never copied, and backup output names the keys to archive separately. Restore never loads a legacy `config.env` and decrypts every credential with separately provisioned keys before running destructive SQL. `bun run db:lifecycle` fails if a new bundle contains `config.env`. Production skips the startup backup gate. | `src/utils/backup/dataBackup.ts`, `src/init/backup.ts`, `scripts/devtools/backupData.ts`, `scripts/checks/validateLifecycle.ts` | A new bundle yields only ciphertext, but its dump still holds private conversations and memories. Bundles created before database-only backups still carry `config.env` beside their dump and remain the whole key set until that file is moved to protected storage or deleted. The separate key archive is now the credential to protect, because a dump plus that archive is a full compromise. |
| **Secret in a subprocess command line** | Any local principal on the host | None today. | `src/utils/backup/dataBackup.ts`, `src/providers/openrouter/openrouterVideoGeneration.ts` | `pg_dump` receives the connection URL (with the database password) as an argument, and the OpenRouter video path passes `Authorization: Bearer <key>` to `curl` as an argument, so both are readable from the process table. The PowerShell branch of the same path passes headers on stdin, which is the pattern to copy. |
| **Secret in a subprocess environment** | Any stdio MCP server | None: children receive `{...process.env, ...configured}`. | `src/utils/mcp/mcpManager.ts`, `src/utils/mcp/mcpConfig.ts` | `mcpConfig` builds a curated per-server environment, but `mcpManager` spreads the full process environment over it, so every MCP package receives the master encryption key, the Discord token, and all provider credentials. Restricting the spread to the curated list is the smallest fix. |
| **Secret in logs, metrics, or error reports** | Log readers, log-file sinks | `log` redacts sensitive field names and scrubs bearer tokens, `key=` parameters, `postgres://user:pass@`, `sk-`, `AIza`, and `nvapi-` shapes in strings, then sanitizes the copies that reach `error_logs`. Production keeps pino at `error` level. | `src/utils/misc/logger.ts`, `src/utils/db/repositories/ErrorLogRepository.ts` | Redaction is pattern-based, so a credential shape outside the list survives if it arrives as a plain string. `log.metric` is the one sink that skips `sanitizeLogPayload` entirely, and two call sites pass raw provider error text into it. |
| **Credential sent to an unintended host** | Any admin or user who can edit a URL, and any host that can answer with a redirect | SSRF validation and DNS pinning on every hop, but the `Authorization` header is preserved across redirects and re-sent. | `src/utils/security/userRemoteFetch.ts`, `src/utils/provider/providerPanelOperations.ts`, `src/providers/custom/*` | Registering or editing an endpoint sends the stored credential of that label to the newly typed URL, and a `302` to another public host carries the header along. This is intended for the label's owner and is not a privilege gain, but it means a leaked or repointed URL is a leaked credential. |
| **Discord bot token via a URL substring match** | Any member who can get the model to run video generation with a message image, plus an enabled ComfyUI video endpoint | None: the guard is a case-insensitive substring test for `discord.com`, `discordapp.com`, `discord.net`, or `discordcdn.com`, run against the whole URL string. | `src/providers/custom/customComfyUiEndpoint.ts`, `src/tools/functionCalls/generateVideoTool.ts`, `src/utils/security/safeDownload.ts` | Any attacker-authored image URL containing `discord.com` (in the host, path, or query) receives `Authorization: Bot $DISCORD_TOKEN` when the raw URL is fetched. Discord's proxy candidate is tried first, so exploitation needs that candidate to fail, and the token is a full bot takeover. Compare `new URL(url).hostname` against the real Discord hosts instead. |

### Database and Secrets

| Threat (STRIDE) | Scenario | Risk | Current Mitigation | Implementation Area | Residual Risk / Assumption |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Tampering / Elevation of Privilege** | SQL injection through Discord messages, slash command options, persona text, imported presets, memories, or endpoint settings. | Critical | Bun SQL tagged template literals for all values; no dynamic `ORDER BY`; `sql.unsafe` call sites use constants. Schema-derived allowlists (`sqlSecurity.ts`) cover four repositories. | `src/utils/db/client.ts`, `src/utils/db/sqlSecurity.ts`, `src/utils/db/repositories/*`, `scripts/checks/lib/sqlAudit.ts` | `ConfigRepository` interpolates `${tableName}` and `${key}` into `SET` with no runtime allowlist, protected only by `Partial<Server*ConfigRow>` typing, which vanishes at runtime. `bun run audit-sql` checks file locations where raw SQL may live; it does not verify whether query values are parameterized. |
| **Information Disclosure** | Cross-server or cross-user leakage from a missing `server_id`, `user_id`, `persona_id`, persona lineage, or Discord channel filter. | High | Application-layer tenant scoping in DB helpers and route handlers; personal and server memory paths are separate; export and delete operations are scope-specific. | `src/utils/db/repositories/*`, `src/utils/discord/interactions/memoriesRoutes.ts`, `src/commands/learn/history.ts`, `src/commands/personal/*`, `src/utils/discord/interactions/configRoutes.ts`, `src/utils/discord/interactions/configPermissionPolicy.ts` | There is no database row-level security policy anywhere in the schema, so correctness depends on query scoping and review. Latent helpers exist that are safe only because of today's callers: `loadVoiceSampleById` is not server-scoped, and `resolveAvatarPath` joins an arbitrary path under `process.cwd()` without a containment check. |
| **Information Disclosure** | Encryption keys are rotated and a version is retired before its rows are re-encrypted. | High | Lazy re-encryption on read for `opt_api_keys`, managed webhook tokens, and guild MCP tokens; versioned keys, with the current version chosen by `CRYPTO_SECRET_CURRENT` or the highest version present. | `src/utils/security/crypto.ts`, `src/utils/db/repositories/ServerRepository.ts`, `src/utils/db/repositories/ToolRepository.ts`, `scripts/devtools/rotateAllKeys.ts`, `scripts/devtools/auditKeyVersions.ts`, `src/utils/security/encryptedColumns.ts` | `bun run rotate-keys` and `bun run audit-keys` cover every encrypted column listed in `encryptedColumns.ts`. Rotation requires `--bot-stopped`, which records the operator's assertion and cannot detect a running instance, and a partial failure leaves earlier rows migrated. Neither command authorizes retiring a version: retained backups still need their archived keys. Production also copies only `CRYPTO_SECRET` through `_V3` from the secrets bundle, so a `_V4` rotation is silently ignored while every component reports success. |
| **Repudiation / Tampering** | A user claims they did not create, edit, or delete memory or configuration. | Medium | Slash commands are Discord-authenticated, and logging includes command, user, and server metadata in many paths. | `src/commands/*`, `src/utils/misc/logger.ts` | Logging provides operational diagnostics rather than a tamper-proof audit log. |
| **Denial of Service** | Large memory imports, document memories, vector operations, or message history imports consume DB or CPU. | Medium | Memory, document, and import caps in `rateLimiter.ts` are applied before writes in roughly thirty call sites, plus quotas and cooldowns. | `src/utils/misc/memoryLimits.ts`, `src/utils/security/rateLimiter.ts`, `src/utils/db/repositories/CooldownRepository.ts` | Reminder creation has no count cap: `reminderTool` writes a row per call and `getUserReminderCount` is used only for display, so a user can grow the table through the model without limit. |
| **Tampering / Stale State** | Caches continue serving old permissions, config, memories, webhooks, or Matrix links after a write. | Medium | Invalidation sits after the write result in every sampled path, and no cache holds a decrypted credential: `credentialResolver` decrypts per call. | `src/utils/cache/*`, `src/utils/bridges/matrix/*`, `src/utils/cache/guildMcpConfigCache.ts`, `src/utils/discord/webhook/webhookCore.ts` | Two caches hold credential material rather than plaintext: `guildMcpConfigCache` caches rows with the encrypted token, and `webhookCache` holds live Discord webhook objects whose tokens the app cannot re-key. New DB writes must invalidate matching caches only after successful writes. |

## 2. Discord Commands, Permissions, and Webhooks

Discord is both the identity provider and the primary execution surface.

| Threat (STRIDE) | Scenario | Risk | Current Mitigation | Implementation Area | Residual Risk / Assumption |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Elevation of Privilege** | A normal user invokes server-management commands to change provider keys, personas, Matrix links, quotas, or memory imports. | High | The loader sets a Discord `ManageGuild` registration default for the `model`, `nsfw`, `server`, `expressions`, `matrix`, and `quota` categories. `/providers`, `/setup`, `/nuke`, `/moderation`, `/matrix link`, `/quota reset`, and `/expressions manage` re-check `memberPermissions` at execution. `/config` is enforced per interaction by a default-deny route policy. | `src/utils/discord/commandLoader.ts`, `src/utils/discord/interactions/providersRoutes.ts`, `src/utils/discord/interactions/configPermissionPolicy.ts`, `src/utils/discord/interactions/configRoutes.ts` | `setDefaultMemberPermissions` is only a default: a guild admin can grant the command to a role in Server Settings, and `src/events/interactionCreate/handleCommands.ts` performs no permission check of its own. Commands with no gate at all are `/persona create`, `/persona export`, `/persona generate`, `/status`, and `/troubleshoot chat`. |
| **Spoofing** | A foreign webhook or bot message is treated as TomoriBot or persona output, poisoning reply attribution or causing response loops. | High | Bot accounts are ignored unless manually triggered. Webhook attribution matches display names, and lookalike names fold together. | `src/utils/chat/admission.ts`, `src/utils/chat/contextPipeline.ts`, `src/utils/chat/triggerProcessor.ts`, `src/utils/chat/webhookIdentity.ts` | A foreign webhook whose name matches a persona is not only attributed as persona output, it also marks the turn as a persona job, which skips the global rate limit, the trigger cooldown, and the text quota. Anyone with webhook permission can therefore generate unmetered turns. |
| **Information Disclosure / Spoofing** | Managed Discord webhook token theft lets an attacker post as a persona. | High | Tokens are encrypted at rest with key versions, tied to a guild and channel, decrypted only to post, and re-encrypted lazily on rotation. Avatar edits are rate limited. | `src/utils/db/repositories/ServerRepository.ts`, `src/utils/discord/webhook/webhookCore.ts`, `src/utils/discord/webhook/avatarEditRateLimit.ts` | If a decrypted token leaks from host memory or a log, Discord treats it as bearer auth for that webhook until it is rotated or deleted. `/nuke` decrypts them to delete them, behind its own `ManageGuild` check. |
| **Information Disclosure** | `/status` prints the server system prompt, context note, endpoint list, and provider posture to any member. | High | The command replies ephemerally, so only the invoker sees the pages. | `src/utils/metrics/status/serverConfigPages.ts`, `src/utils/metrics/status/statusDashboard.ts`, `src/utils/metrics/status/command.ts` | There is no permission gate on `/status` and no category filtering in the dashboard, so a member can read up to roughly a thousand characters of the configured system prompt and context note. This bypasses the `prompt_snapshot_enabled` gate that is supposed to control prompt disclosure. |
| **Tampering** | LLM-driven `manage_message` pins, edits, or deletes messages unexpectedly. | Medium | Runtime checks limit edit and delete to direct bot messages or managed persona webhook messages; pin requires `ManageMessages`; message refs are opaque `ref_N` handles in prompt context. | `src/tools/functionCalls/manageMessageTool.ts`, `src/utils/text/messageIdMap.ts` | The `manage_message` feature flag is checked when the tool is advertised, while execution dispatch omits this check. The tool runs with bot permissions, never the invoking human's. |
| **Tampering** | LLM-driven `create_thread` creates unwanted channels of conversation. | Medium | `execute()` re-checks the flag, the blocklist, bot `CreatePublicThreads` and `SendMessagesInThreads`, and target visibility; ambiguous names fail closed; threads are never created inside threads. | `src/tools/functionCalls/createThreadTool.ts`, `src/utils/discord/targetResolver.ts` | The thread is created with bot permissions. Disable the feature flag where thread creation should stay manual. |
| **Information Disclosure** | `cross_channel_message` peeks into a channel and leaks recent messages back to another channel. | High | Runtime requires bot `ViewChannel` and the invoking member's `ViewChannel` on the target, and the server blocklist covers configured channels and forum or media parents. | `src/tools/functionCalls/crossChannelMessageTool.ts`, `src/utils/discord/interactions/configChannelRoutes.ts` | There is no cross-channel feature flag anywhere in the codebase, so the blocklist is the only per-channel control. Server admins should block sensitive channels outright. |
| **Information Disclosure** | Hidden tool notices or fallback details leak private-channel activity into a public thought-log channel. | Medium | Hidden notices are suppressed for DMs and for channels configured as private, including a thread's parent. | `src/utils/discord/toolProgressNotice.ts` | A channel that is private only through Discord permission overwrites is not recognized as private, so its hidden notices, which can include prompt previews, are mirrored to the thought log. Treat thought-log channels as sensitive operational logs. |
| **Denial of Service** | Users spam interactions, message triggers, edits, webhooks, or Discord API calls to hit rate limits. | Medium | Discord.js handles 429s; command cooldowns are per user and cross-guild; trigger cooldowns, stream locks, queues, quotas, and emergency memory-pressure cooldowns exist. | `src/utils/db/repositories/CooldownRepository.ts`, `src/utils/security/rateLimiter.ts`, `src/events/rateLimit/rateLimitLogger.ts`, `src/events/interactionCreate/handleCommands.ts` | `ManageGuild` users are exempt from trigger cooldowns for trigger types 1 to 3, reversible with `DISABLE_COOLDOWN_EXEMPTIONS=true`. Trigger cooldown checks fail open when the database errors, so a database brownout is a spam window. |

## 3. LLM, Prompt, Persona, and Tool Execution

LLM output is untrusted. The model can be manipulated by users, memories, documents, web pages, tool results, MCP descriptions, and persona prompts.

| Threat (STRIDE) | Scenario | Risk | Current Mitigation | Implementation Area | Residual Risk / Assumption |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Tampering** | Prompt injection or jailbreak causes persona drift, unsafe instructions, or attempts to reveal system or developer prompt content. | Medium | Context assembly separates system, persona, tool, and history blocks, and built-in behavior is enforced in TypeScript where possible. | `src/utils/text/contextBuilder.ts`, `src/utils/text/context/*`, `src/events/messageCreate/tomoriChat.ts` | Perfect prompt-injection defense is impossible. Treat every generated tool call as hostile until execution code has checked it. The server system prompt is not confidential: `/status` shows it to any member. |
| **Information Disclosure** | `/tool prompt snapshot` and the `/context` View buttons expose the assembled prompt, memories, messages, media references, or system instructions. | High | One shared gate (`canViewPromptText`): `ManageGuild` bypasses, otherwise `prompt_snapshot_enabled` must allow non-admin access. The `/context` button route re-checks it on every click and disables the view when it fails closed. | `src/utils/text/promptInspection/delivery.ts`, `src/utils/discord/interactions/contextRoutes.ts`, `src/utils/discord/ui/contextUsagePanel.ts` | Enabling prompt snapshots for non-admins intentionally expands disclosure. `/context` also shows the model, provider, context window, estimated cost, and last-reply token count to every member, and `/status` discloses the system prompt with no gate at all, so this gate does not bound prompt disclosure on its own. |
| **Information Disclosure** | A stored credential reaches prompt text. | High | Cleared: context assembly injects database text fields and tool schemas only, no config object is serialized, prompt snapshot uses the resolved credential solely to decide whether the answering provider is personal, no tool takes a credential parameter, and the thought log renders model text only. | `src/utils/text/context/templates.ts`, `src/utils/text/promptInspection/assemble.ts`, `src/tools/**` | One conditional path: a key parked inside an endpoint URL would surface through a redirect error message and from there into a tool result and the model's context. Keep credentials in the credential column, never in a URL. |
| **Tampering / Information Disclosure** | RAG, server memories, personal memories, imported memories, documents, or SillyTavern presets poison future context or leak sensitive content to later generations. | High | Memory scopes are separated, personal privacy levels can block personal memory use, server and user limits exist, and management, export, and remove commands are scoped. | `src/utils/misc/memoryLimits.ts`, `src/utils/discord/interactions/memoriesRoutes.ts`, `src/commands/learn/history.ts`, `src/commands/personal/config.ts` | Server-wide memory is inherently shared. Moderators must remove poisoned or sensitive server memory. |
| **Elevation of Privilege** | A user prompt causes an unauthorized tool call. | High | Built-in tool availability is filtered before advertisement, and high-impact tools re-check their own runtime conditions. `reviewCapabilities` gates operational details, including rotation pool size, on the invoking member's `ManageGuild` and fails closed in DMs. | `src/tools/toolRegistry.ts`, `src/tools/availability.ts`, `src/tools/functionCalls/*`, `src/tools/functionCalls/reviewCapabilities.ts` | Feature flags are advertisement-only: `requiresFeatureFlag` is evaluated in `availability.ts`, while dispatch re-checks availability and context but not the flag, so a call that reaches dispatch runs even with the flag off. There is no universal execution-layer RBAC gate, so new tools must fail closed inside `execute()`. |
| **Information Disclosure** | Opaque Discord snowflakes, raw message IDs, or media IDs appear in prompt context and are reused incorrectly. | Medium | Recent-message targets are exposed as opaque `media_N` and `ref_N` handles and resolved back before execution. | `src/utils/text/messageIdMap.ts`, `src/tools/toolRegistry.ts` | The handles are cosmetic: resolution leaves an unrecognized value untouched, so a raw snowflake still works in every media tool. |
| **Denial of Service / Cost Exhaustion** | Long prompts, recursive requests, tool loops, video or image generation, or repeated retries consume tokens and provider credits. | High | Message fetch limits, media windows, token and context trimming, stream flood guards, cooldowns, and text, image, and video quotas. | `src/utils/security/rateLimiter.ts`, `src/utils/quota/*`, `src/events/messageCreate/tomoriChat.ts`, `src/utils/discord/streamOrchestrator.ts` | Admins must configure quotas and feature flags for their risk tolerance. A persona-named foreign webhook bypasses metering entirely (section 2). |

## 4. MCP and Web/Search Tools

TomoriBot supports bundled MCP servers, a REST-backed Brave engine consumed internally by the unified `web_search` tool's dispatcher, bundled URL fetching consumed internally by the unified `fetch_url` dispatcher, optional self-hosted SearXNG and Crawl4AI servers, and guild-registered remote MCP servers. The search chain is Brave, then SearXNG, then DuckDuckGo, then IAsk; the last two run through the bundled third-party stdio MCP server.

| Threat (STRIDE) | Scenario | Risk | Current Mitigation | Implementation Area | Residual Risk / Assumption |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Elevation of Privilege** | A local MCP server runs malicious code on the host. | Critical | Local MCP servers are operator-controlled deployment components, and TomoriBot does not sandbox the process or its filesystem access. | `src/utils/mcp/mcpManager.ts`, `src/tools/mcpServers/*` | Two aggravating facts: stdio children are spawned with `{...process.env, ...configured}`, so the curated per-server environment in `mcpConfig.ts` is overridden by the full bot environment, and the bundled DuckDuckGo search server that ships enabled is a third-party package. Any MCP server therefore reaches `CRYPTO_SECRET`, the Discord token, the database URL, and every provider key. Run only trusted MCP servers, under least-privilege OS or container accounts. |
| **Information Disclosure** | Remote guild MCP URL points at localhost, RFC1918, link-local, metadata IPs, or other internal services. | High | Remote URL validation blocks private, reserved, and loopback addresses in production, requires HTTPS in production, allows localhost HTTP only outside production, and runs before each HTTP transport request. Pinning is a literal-IP rewrite with Host and TLS SNI, retried across validated addresses and failed closed when an address cannot be pinned. Redirects are revalidated per hop. | `src/utils/security/remoteUrlSecurity.ts`, `src/utils/security/userRemoteFetch.ts`, `src/utils/mcp/guildMcpManager.ts`, `src/utils/mcp/smitheryConnection.ts` | Guild registrations on `*.run.tools` with a key connect through Smithery Connect: the key goes only to the pinned `api.smithery.ai` origin through the guarded fetcher, but Smithery receives all of that registration's tool traffic and fetches the upstream itself, beyond the bot's URL gate. |
| **Information Disclosure** | A crafted URL reaches cloud instance metadata. | High | An always-on denylist runs in both the pre-dispatch gate and the connection and redirect gate, and neither the development auto-relax nor `FETCH_URL_ALLOW_PRIVATE_NETWORK` can bypass it. ## Security Follow-Ups

These items are concrete hardening tasks from the residual-risk column. Keep this section focused on implementation work rather than general advice.

### Should Fix

| Area | Issue | Suggested Action |
| :--- | :--- | :--- |
| Discord token | `buildDiscordDownloadInit()` attaches `Authorization: Bot` to any URL whose text contains `discord.com`. | Match `new URL(url).hostname` against Discord's real hosts and drop the header for anything else. |
| MCP environment | `mcpManager` spawns stdio children with `{...process.env, ...configured}`, overriding the curated list and handing children the master key and every credential. | Spread only the curated per-server environment, and pass through an explicit allowlist for anything a server genuinely needs. |
| `/status` | Server configuration pages, including the system prompt and context note, render for any member with no permission gate. | Gate the server config pages on `ManageGuild`, or remove the prompt fields from the member-visible dashboard. |
| Tool execution | Feature flags are evaluated when tools are advertised, and dispatch re-checks availability but not the flag. | Re-check `requiresFeatureFlag` inside dispatch, and keep the fail-closed checks for quota, permissions, and target ownership in `execute()`. |
| Guild MCP names | The collision filter runs at advertisement only, while dispatch prefers a guild MCP by raw name over the built-in. | Apply the same collision filter inside `isGuildMCPFunction` so a hidden name can never execute. |
| Guild `url_fetcher` | Replacing the built-in `fetch_url` drops the size cap and the metadata denylist for that server. | Run the guild fetch path through the same pre-dispatch gate and byte cap as the built-in engine. |
| Key rotation | Production ignores `CRYPTO_SECRET_V4` and later. | Copy version variables generically instead of naming V1 through V3. |
| Heap snapshots | Production arms a `SIGUSR2` handler that writes plaintext secrets into the host log mount. | Leave `HEAP_SNAPSHOT_DIR` unset by default in production, and treat enabling it as an incident-time decision with the directory cleaned afterward. |
| Process arguments | `pg_dump` receives the database URL and the curl branch receives the bearer token as arguments. | Pass the dump connection through `PGPASSWORD` or a passfile, and feed curl its headers from stdin or a config file the way the PowerShell branch already does. |
| Matrix media | Size is checked after the body is buffered, a malformed cap disables the check, and the media path is composed from attacker-controlled segments. | Stream with a hard byte cap, validate the parsed cap, and resolve the media path through a strict segment allowlist. |
| Log metrics | `log.metric` bypasses `sanitizeLogPayload`, and two call sites pass raw provider error text into it. | Sanitize metric payloads, or route error text through `sanitizeLogPayload` at those two call sites. |
| Custom endpoints | `registerCustomEndpoint` loads an endpoint by ID without an owner predicate. | Add the owner predicate to the service lookup so the guard does not live only in the caller. |

### Operational Hardening

| Area | Action |
| :--- | :--- |
| MCP | Document that shell, file, database, or broad-network MCP servers are equivalent to granting host or internal-network access, and that stdio children inherit the bot environment. |
| Matrix | Document production appservice exposure requirements, the need to keep the listener off public interfaces, token rotation, and room moderation for `/kill`, `/refresh`, and inbound media. |
| Secrets | Document the rotation procedure after provider key, webhook token, Matrix token, or host compromise, including that retiring a `CRYPTO_SECRET` version is only safe once every encrypted table has been re-encrypted. |
| Secret strength | Require a high-entropy `CRYPTO_SECRET` at startup, since the pgcrypto passphrase has no application-side KDF and a dump plus a weak secret is a full compromise. |
| Discord permissions | Recommend least-privilege bot channel access, and note that several tools operate with bot visibility rather than the invoker's. |
| Quotas and feature flags | Recommend conservative defaults for image, video, web fetch, prompt snapshot, and manage-message, and restrict `/providers`, MCP registration, and the cross-channel blocklist. |
| Diagnostics | Restrict who can signal the container and who can read the log, backup, and data mounts, and treat a heap snapshot or legacy backup bundle as production credentials. Keep the encryption key archive apart from backups. |

## Contributor Checklist

1. Enforce security in TypeScript rather than relying on prompts, and re-check feature flags, permissions, quotas, and target ownership inside `execute()`.
2. Use `fetchUserRemoteUrl()` or `validateRemoteUrl()` for user-supplied or admin-configured remote endpoints unless the URL is a fixed first-party provider URL, and compare parsed hostnames rather than substrings when attaching a credential.
3. Use `safeDownload()` or equivalent size, timeout, and streaming-cap checks for user-controlled media.
4. Use Bun SQL template literals for values and `sqlSecurity.ts` helpers for dynamic columns; never interpolate identifiers that a request can shape.
5. Scope all database reads and writes by server, user, persona, or channel as appropriate.
6. Invalidate caches after successful writes, in the same code path.
7. Never render a credential, prefill one into a component, or serialize a configuration object into prompt text, logs, exports, or a subprocess argument.
8. Treat MCP definitions, MCP results, web pages, documents, memories, imports, provider error bodies, and custom endpoint responses as untrusted prompt content.
9. Treat host diagnostics (heap snapshots, legacy backup bundles) as credential-bearing, and keep `.env` out of anything that travels.
