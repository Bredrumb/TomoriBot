Renderize páginas web com uso intenso de JavaScript em Markdown limpo para o TomoriBot usando um servidor local do [Crawl4AI](https://github.com/unclecode/crawl4ai).

A ferramenta integrada `fetch_url` usa o motor leve `safe_http` por padrão. O Crawl4AI adiciona um navegador Playwright headless opcional que executa scripts no lado do cliente e extrai o conteúdo da página antes de retornar o Markdown para o bot.

Como o Crawl4AI segue redirecionamentos fora do cliente HTTP protegido do TomoriBot, ele só é admitido quando a busca em rede privada é permitida, o que exige `FETCH_URL_ALLOW_PRIVATE_NETWORK=true` em todos os `RUN_ENV`. Essa configuração também permite que o `fetch_url` leia páginas de localhost e da LAN, portanto ative-a apenas em uma instância cujos membros sejam confiáveis.

:::caution[O que o TomoriBot consegue e não consegue verificar]
O TomoriBot recusa uma URL cujo nome de host não resolve, ou resolve para um endereço de metadados de nuvem, antes de pedir ao Crawl4AI que a abra. Ele não consegue controlar o que o navegador faz em seguida: o Crawl4AI resolve o nome novamente, segue redirecionamentos e carrega imagens e scripts por conta própria. O bloqueio permanente de metadados do TomoriBot não cobre essas solicitações.

A imagem fixada (`unclecode/crawl4ai:0.9.4`) envia o navegador por meio de seu próprio proxy, que bloqueia endereços privados, de loopback e de metadados em toda solicitação e redirecionamento. Deixe `CRAWL4AI_ALLOW_INTERNAL_URLS` sem definição: defini-la como `true` desativa esse proxy, inclusive para metadados.
:::

O Crawl4AI 0.9.4 exige um token de API antes de aceitar conexões de fora do próprio contêiner. Gere um token aleatório (por exemplo com `openssl rand -hex 32` ou `docker run --rm alpine:3.22 sh -c "head -c 24 /dev/urandom | base64"`) e salve-o como `CRAWL4AI_TOKEN` no `.env` em todos os caminhos de configuração abaixo. Sem ele, o contêiner inicia, mas o TomoriBot não consegue alcançá-lo e faz fallback para `safe_http`.

Escolha um caminho de configuração:

### Opção A: Docker Compose (quando o TomoriBot roda no Docker)

Use este caminho se você executa o TomoriBot com a pilha Docker Compose do repositório. Primeiro, defina `CRAWL4AI_BASE_URL=http://crawl4ai:11235/`, `CRAWL4AI_TOKEN` e `FETCH_URL_ALLOW_PRIVATE_NETWORK=true` no `.env`.

Em seguida, inicie com:

```sh
docker compose --profile fetch-crawl4ai up -d
```

Isso inicia a pilha do Compose com o contêiner do Crawl4AI na rede Docker do TomoriBot. O Compose repassa `CRAWL4AI_TOKEN` ao contêiner como `CRAWL4AI_API_TOKEN`, e o TomoriBot envia esse valor como token bearer. A porta 11235 é publicada apenas em `127.0.0.1`, para depuração local; o próprio TomoriBot se conecta pela rede Docker.

Se você executa o TomoriBot diretamente com `bun run dev`, use o caminho autônomo abaixo.

Se você também quiser o SearXNG, encadeie os perfis:

```sh
docker compose --profile searxng --profile fetch-crawl4ai up -d
```

### Opção B: Docker autônomo (ao executar `bun run dev`)

Primeiro, defina `CRAWL4AI_BASE_URL=http://localhost:11235/`, `CRAWL4AI_TOKEN` e `FETCH_URL_ALLOW_PRIVATE_NETWORK=true` no `.env` para que o bot se conecte à porta do contêiner publicada em `127.0.0.1`.

Depois, em vez de executar o TomoriBot diretamente com `bun run dev`, use `bun run launch --crawl4ai`. Isso gerencia o ciclo de vida do contêiner automaticamente e aguarda o servidor ficar saudável antes de iniciar o bot. Ele para com um erro se `CRAWL4AI_TOKEN` estiver ausente:

```sh
bun run launch --crawl4ai
```

Se você também quiser o SearXNG:

```sh
bun run launch --searxng --crawl4ai
```

Se você preferir gerenciar o contêiner manualmente, mantenha `CRAWL4AI_BASE_URL=http://localhost:11235/` no `.env` e inicie o contêiner com o token correspondente armazenado em `CRAWL4AI_API_TOKEN`, sem colocar o segredo no histórico do shell:

### Opção C: Sem servidor de renderização por navegador

Deixe `CRAWL4AI_BASE_URL` sem definição. A ferramenta `fetch_url` usará o motor protegido `safe_http`.

## Ordem de inicialização

O TomoriBot verifica a integridade do servidor na primeira chamada de `fetch_url` após a inicialização e armazena o resultado em cache por 60 segundos. Se o contêiner não estiver pronto quando essa primeira verificação ocorrer, o bot o tratará como indisponível pelo minuto seguinte.

Para Docker autônomo, inicie o contêiner do Crawl4AI antes de iniciar o TomoriBot. `bun run launch --crawl4ai` já faz isso para você.

### Configuração pela primeira vez

### Atualizando a partir de `latest`

Um contêiner `crawl4ai` existente mantém a imagem a partir da qual foi criado, portanto `docker start` não o atualiza. Remova-o uma vez e depois use seu caminho de configuração novamente:

```sh
docker rm -f crawl4ai
```

Com o Compose, `docker compose --profile fetch-crawl4ai up -d` recria o contêiner a partir da imagem fixada.

### Retornando após uma reinicialização

Se o contêiner já existir de uma execução anterior, use `docker start` em vez de `docker run` para evitar conflito de nome:

```sh
docker start crawl4ai
docker ps
```

Depois inicie o TomoriBot normalmente. Reiniciar `bun run dev` limpa o cache de integridade em memória, então, desde que o contêiner esteja pronto antes, o motor correto será selecionado imediatamente.

## Injeção de cookies

O Crawl4AI suporta injetar cookies no navegador para que o navegador headless apareça já autenticado ao buscar uma página. Isso é útil para sites que exigem sessão para visualizar o conteúdo (ex.: notícias com paywall, fóruns privados, painéis restritos por login).

O fallback `safe_http` não suporta injeção de cookies. Os cookies só são aplicados quando o Crawl4AI está ativo.

:::note[Limites da detecção de bots]
A injeção de cookies contorna barreiras de login, mas não fingerprinting de bots. Sites com detecção agressiva contra bots (notavelmente Twitter/X) detectam o Playwright headless via fingerprinting de canvas/WebGL e retornam páginas vazias mesmo com cookies de sessão válidos. A injeção de cookies funciona bem para sites que restringem apenas por autenticação.
:::

### Obtendo seus cookies

1. Abra o navegador e faça login no site desejado.
2. Abra as Ferramentas do Desenvolvedor (`F12`) > aba `Application` > `Storage` > `Cookies` > selecione o domínio do site.
3. Copie o `Value` de cada cookie necessário (normalmente um token de sessão; verifique os nomes dos cookies do site).

### Crawl4AI

Defina `CRAWL4AI_COOKIES_JSON` no `.env` como um array JSON:

```dotenv
CRAWL4AI_COOKIES_JSON=[{"name":"session","value":"YOUR_SESSION_TOKEN","domain":".example.com"}]
```

Quando essa variável está definida, `fetch_url` alterna automaticamente do endpoint `/md` para `/crawl` com `browser_config.cookies`. O `/md` não suporta injeção de cookies.

### Campos do objeto de cookie

| Campo | Obrigatório | Descrição |
|---|---|---|
| `name` | Sim | Nome do cookie |
| `value` | Sim | Valor do cookie |
| `domain` | Não | Escopo de domínio (ex.: `.x.com`). Recomendado para maior precisão. |
| `path` | Não | Escopo de caminho. Usa `/` por padrão se omitido. |

:::caution[Proteja tokens de sessão]
Valores de cookies são sensíveis, portanto trate-os como senhas. Eles concedem acesso total de sessão à sua conta. Não envie o `.env` para o controle de versão.
:::

## Variáveis de ambiente

| Variável | Padrão | Descrição |
|---|---|---|
| `CRAWL4AI_BASE_URL` | não definido | Habilita o Crawl4AI quando definida: o TomoriBot tenta usá-lo primeiro e faz fallback para `safe_http` quando estiver fora do ar ou uma busca falhar. Ignorada a menos que `FETCH_URL_ALLOW_PRIVATE_NETWORK=true`. Use `http://crawl4ai:11235/` no Docker Compose, ou `http://localhost:11235/` quando o TomoriBot rodar diretamente na sua máquina. |
| `CRAWL4AI_TOKEN` | não definido | Token bearer obrigatório. Deve corresponder a `CRAWL4AI_API_TOKEN` no contêiner do Crawl4AI, que recusa conexões externas sem ele. |
| `FETCH_URL_TIMEOUT_MS` | `15000` | Tempo limite de solicitação por motor para o Crawl4AI e para os outros motores de busca de URL. |
| `FETCH_URL_MAX_CONTENT_LENGTH` | `50000` | Máximo de caracteres retornados por uma chamada de busca antes que continuação seja necessária. |
| `FETCH_URL_ALLOW_PRIVATE_NETWORK` | `false` | Obrigatória para o Crawl4AI em todos os `RUN_ENV`. Também permite que `fetch_url` leia localhost, LAN e outros endereços privados, inclusive via HTTP simples. Endereços de metadados de nuvem continuam bloqueados. |
| `FETCH_URL_FILTER_MODE` | `fit` | Modo de filtro do `/md` do Crawl4AI. `fit` mantém o Markdown mais limpo para uso em LLM; `fetch_url(..., raw=true)` substitui essa opção por solicitação. |
